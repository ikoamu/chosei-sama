# ドメインドキュメント

エンジニアリングスキルがコードベースを探索する際に、このリポジトリのドメインドキュメントをどう参照するか。

## 探索の前に読むもの

- リポジトリ直下の **`CONTEXT.md`**、または
- リポジトリ直下に **`CONTEXT-MAP.md`** があればそれ — コンテキストごとの `CONTEXT.md` を指す。トピックに関連するものをそれぞれ読む。
- **`docs/adr/`** — これから作業する領域に触れる ADR を読む。マルチコンテキストの場合は `src/<context>/docs/adr/` のコンテキスト固有の決定も確認する。

これらのファイルが存在しない場合は **黙って続行** する。不在を指摘したり、事前作成を提案したりしない。生成側スキル（`/grill-with-docs`）が、用語や決定が実際に確定したときに随時作成する。

## ファイル構成

シングルコンテキストのリポジトリ（大半のリポジトリ）:

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

マルチコンテキストのリポジトリ（直下に `CONTEXT-MAP.md` がある）:

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← システム全体の決定
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← コンテキスト固有の決定
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## グロッサリの語彙を使う

出力がドメイン概念に言及するとき（イシュータイトル、リファクタ提案、仮説、テスト名）、`CONTEXT.md` で定義された用語を使う。グロッサリが明示的に避けている同義語に流れない。

必要な概念がまだグロッサリにない場合、それは合図 — プロジェクトが使っていない言葉を発明している（再考すべき）か、本当にギャップがある（`/grill-with-docs` 用にメモ）かのどちらか。

## ADR との矛盾を指摘する

出力が既存の ADR と矛盾する場合、黙って上書きせず明示的に指摘する:

> _ADR-0007（イベントソース型 orders）と矛盾 — ただし再検討の価値あり。理由は…_
